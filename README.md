# Тріаж вхідних запитів AI-юніту

Внутрішні команди пишуть в AI-юніт у вільній формі — у Slack, Telegram, поштою.
Перш ніж брати запит у роботу, його треба зрозуміти: про що він, чий, наскільки
терміново і чи взагалі можна за нього братися як є.

Цей сервіс читає вивантаження такого інбоксу, проганяє кожен запит через LLM,
**валідує відповідь у строгу схему** і віддає структурований `output.json` та
зведений `report.md` з чергою на уточнення.

```
CSV → нормалізація → [async, з обмеженням частоти] → LLM (structured output)
                                                       │
                             ┌─────────────────────────┴─── помилка
                             │                              │
                        валідація                    ретрай / repair-промпт
                             │                              │
                      бізнес-правила              запис зі status="failed"
                             │                              │
                             └──────────┬───────────────────┘
                                        ▼
                            output.json  +  report.md
```

**Головна властивість: кожен вхідний рядок дає рівно один вихідний запис.**
Запит може не обробитися — модель здатна намолоти дурниць, API повернути 429,
мережа відвалитися — але зникнути він не може. Помилки це теж дані: вони
лягають у результат зі `status="failed"`, причиною і останньою сирою відповіддю
моделі.

## Швидкий старт

### Без API-ключа

Весь пайплайн можна прогнати офлайн на детермінованому стабі — щоб подивитися,
як воно влаштоване, ключ не потрібен:

```bash
python -m venv .venv && ./.venv/bin/pip install -r requirements.txt
PYTHONPATH=src ./.venv/bin/python -m triage --provider fake
```

Стаб — це матчер за ключовими словами, а не класифікатор. Він ніколи не
підставляється замість справжнього провайдера мовчки: `fake` треба попросити
явно, щоб ніхто не переплутав вивід заглушки з виводом моделі.

### З Gemini

```bash
cp .env.example .env     # і вписати GEMINI_API_KEY
PYTHONPATH=src ./.venv/bin/python -m triage
```

Безкоштовний ключ береться за хвилину в [Google AI Studio](https://aistudio.google.com/apikey).
Картка не потрібна. `.env` у `.gitignore`.

### Docker

```bash
docker build -t request-triage .
docker run --rm --env-file .env -v "$(pwd)/output:/app/output" request-triage
```

## Конфігурація

Усе читається з оточення (або з `.env`), прапорці CLI мають пріоритет.

| Змінна | Прапорець | Дефолт | Навіщо |
|---|---|---|---|
| `LLM_PROVIDER` | `--provider` | `gemini` | `gemini` або `fake` |
| `GEMINI_API_KEY` | — | — | ключ; у репозиторій не потрапляє |
| `GEMINI_MODEL` | `--model` | `gemini-3.1-flash-lite` | запінено навмисно, див. нижче |
| `GEMINI_THINKING_BUDGET` | — | `0` | `0` — без «мислення», `auto` — на розсуд моделі |
| `MAX_CONCURRENCY` | `--concurrency` | `4` | скільки викликів одночасно |
| `REQUESTS_PER_MINUTE` | `--rpm` | `5` | під квоту free tier; `0` вимикає |
| `MAX_ATTEMPTS` | — | `4` | спроб на один запит |
| `REQUEST_TIMEOUT_S` | — | `60` | таймаут одного виклику |
| — | `--input` | `data/input_requests.csv` | вхідний файл |
| — | `--outdir` | `output` | куди писати результат |
| — | `--limit` | — | обробити лише перші N (дешевий смоук-тест) |

Коди виходу: `0` — усе оброблено, `2` — завершилось, але є невдалі рядки,
`1` — запуск не відбувся. Це щоб сервіс можна було поставити в cron чи CI.

## Що на виході

**`output.json`** — об'єкт, а не голий масив: поруч із даними лежить
провенанс прогону (коли, якою моделлю, скільки токенів, скільки помилок).
Голий масив каже, що вирішили, але не каже ким і якою ціною — а це саме те,
що хочеться знати, коли два прогони розійшлися.

```jsonc
{
  "schema_version": "1.0.0",
  "generated_at": "...",
  "provider": "gemini",
  "model": "gemini-3.5-flash",
  "stats": { "total": 18, "ok": 18, "failed": 0, "prompt_tokens": ... },
  "requests": [
    {
      "id": "REQ-001", "channel": "Slack", "status": "ok",
      "triage": {
        "category": "звіт/аналітика",
        "target_department": "маркетинг",
        "priority": "medium",
        "short_summary": "...",
        "requested_actions": ["..."],
        "needs_clarification": false,
        "confidence": 0.9,
        "clarifying_questions": [],
        "mentioned_systems": ["Google Ads"],
        "is_actionable": true
      },
      "error": null,
      "meta": { "attempts": 1, "applied_rules": [], "prompt_tokens": 1757 }
    }
  ]
}
```

**`report.md`** — агрегати по категоріях, пріоритетах і відділах, окремо черга
на уточнення (з конкретними питаннями до замовника), список високопріоритетних,
список невдалих і перелік спрацьованих бізнес-правил.

## Схема

Шість полів — обов'язкові за завданням. Ще чотири я додав; кожне мусить
виправдати своє існування конкретним рядком із наданого інбоксу, інакше це
просто зайві токени:

| Поле | Навіщо | Приклад із даних |
|---|---|---|
| `confidence` (0–1) | напарник до `needs_clarification`: дозволяє автоматично відправляти на людину все, у чому модель невпевнена, навіть якщо вона сама цього не визнала | пороговане правилом R3 |
| `clarifying_questions` | «розмито» — це діагноз, а не дія. Питання перетворюють прапорець на наступний крок, який можна одразу відправити замовнику | REQ-002 «хлопці треба бот», REQ-011 «нам би табличку якусь» |
| `mentioned_systems` | роутинг на інженера, який знає цю систему, і оцінка, які інтеграції потрібні | PlanFix, BigQuery, Google Ads, Meta — трапляються у 10 із 18 запитів |
| `is_actionable` | відсікає те, що взагалі не одиниця роботи, не змішуючи це з «поза скоупом за темою» | REQ-008 «дякую за вчора 🙌» |
| `domain` | **предметна область запиту**, на відміну від `target_department` — відділу-замовника | див. нижче |

## Рішення, які варто пояснити

**`target_department` і `domain` — це два різні питання.** Спершу поле було
одне. Перший живий прогін повернув `null` у відділі на 9 рядках із 12 — і це
коректно: інбокс майже ніколи не називає відправника, а промпт забороняє
вгадувати. Але звіт від цього виявився наполовину порожнім, бо одне поле
намагалося відповісти на два питання одразу. Тепер `target_department` лишається
суворим (**хто просить**, `null` якщо в тексті не сказано), а `domain` —
обов'язковим (**про що запит**, виводиться з теми). Словник у них спільний, тож
у звіті вони стоять поруч і їх видно як дві різні картини.

**Категорії перетинаються, тому в промпті зафіксований каскад.**
«Автоматизувати щотижневий звіт» (REQ-001) — це чесно і автоматизація, і
звітність. Замість того щоб робити вигляд, ніби існує одна правильна відповідь,
задано явний порядок пріоритету: поза скоупом → баг → консультація → інтеграція
→ звіт → автоматизація. Це продуктове рішення, а не істина, але воно робить
вивід відтворюваним, а агрегати — порівнюваними між прогонами. Порядок лежить
в одному місці й міняється за хвилину.

**Словники закриті.** `category`, `priority` і `target_department` —
переліки, а не вільні рядки. Вільний рядок дав би «маркетинг», «Маркетинг»,
«відділ маркетингу» і «marketing» як чотири різні відділи, і звіт розсипався б.
Значення підставляються в промпт із тих самих Python-перелічень, якими потім
валідуються, тож промпт і валідатор не можуть розійтися.

**Structured output і pydantic — обидва, не один.** Схема на боці API прибирає
цілий клас багів (модель загорнула JSON у ```-огорожу). Але вона не вміє в
міжпольові правила, і провайдер без цієї фічі мовчки забрав би гарантію. Тому
жорсткі ворота — все одно pydantic, з `extra="forbid"`.

**Бізнес-правила окремо від валідації.** Валідація відповідає на питання
«чи коректно сформовано». Правила — на питання «чи не суперечить воно саме
собі»: модель уміє повернути ідеально типізований об'єкт, у якому
`needs_clarification=false` стоїть поруч із `confidence=0.2`. Кожне спрацювання
пишеться в `meta.applied_rules`, тож сира думка моделі завжди відрізняється від
нашої постобробки.

**Few-shot приклади — синтетичні.** Вони покривають форми, на яких модель
спотикається (порожній запит, подяка, два прохання в одному повідомленні), але
жоден не взятий із реального інбоксу — інакше я б просто підказав відповіді на
той самий файл, на якому потім і міряю якість.

**Модель запінена, а не через аліас, і обрана за квотою.**
`gemini-flash-latest` змінюється під тобою — при тому, що весь сенс
`temperature=0` і фіксованого `seed` саме у відтворюваності. Дефолт при цьому
обраний **за розміром безкоштовної добової квоти, а не за потужністю**:
детальніше в розділі про квоти нижче, разом із рештою того, що з'ясувалося
лише під час живих прогонів.

**Запит — це дані, а не інструкції.** `raw_text` пишуть люди, і REQ-014 уже
містить URL. Текст обгортається явними маркерами, а в системному промпті сказано
не виконувати вказівок ізсередини й не ходити за посиланнями.

## Де рішення ламається

### Невалідний вивід LLM — закрито

П'ять шарів, від найдешевшого до найдорожчого:

1. **Схема на боці API.** `response_schema` у Gemini обмежує саму генерацію.
   Прибирає цілий клас проблем (огорожі з трьох лапок, преамбула перед JSON).
2. **Толерантне витягування.** Якщо модель усе одно щось дописала — виколупуємо
   об'єкт із тексту. Дешевше за ще один виклик.
3. **Нормалізація відомих вивертів.** `"невідомо"` замість `null`, одиничний
   рядок замість списку з одного елемента — приводяться до типу *перед*
   валідацією. Суворість щодо форми, поблажливість до кількох способів написати
   «тут нічого немає».
4. **Валідація pydantic** — жорсткі ворота, `extra="forbid"`.
5. **Repair-промпт.** Моделі показують її ж зламаний вивід і претензію
   валідатора. Це виправляє більшість промахів із переліками за один виклик.

Що не закрито: **валідний, але неправильний вивід**. Схема ловить
`priority: "urgent"`, але не ловить упевнено помилкову категорію. Ця діра
принципова, і закривається вона не кодом, а розміченим набором для оцінки —
чого тут немає (див. нижче).

### Великий обсяг — закрито частково

Закрито: async із обмеженням паралельності, рівномірний пейсинг під квоту,
запобіжник, що зупиняє безнадійний прогін.

Не закрито:
- **Усе тримається в пам'яті.** Список записів і один JSON-документ. На 18
  рядках байдуже, на 100 тисячах — ні. Лікується потоковим записом (JSONL).
- **Немає чекпоінтів.** Падіння на 900-му рядку з 1000 втрачає весь прогін.
  Лікується файлом стану і пропуском уже оброблених.
- **Немає кешу.** Повторний прогін на тих самих даних платить повторно.
  Лікується кешем за хешем `raw_text` + версії промпту.

### Недетермінізм — закрито частково

`temperature=0`, фіксований `seed`, **запінена модель, а не аліас**. Останнє
важливіше, ніж здається: `gemini-flash-latest` змінюється під тобою, і тоді всі
попередні прогони стають непорівнюваними.

Але детермінізму це не гарантує: провайдери батчать запити, маршрутизують через
MoE-шари й оновлюють моделі. `scripts/check_determinism.py` міряє дрейф замість
того, щоб робити вигляд, ніби його немає. Емпірично поля класифікації стабільні
значно краще за дослівний текст `short_summary` — тому агрегати у звіті
рахуються саме за полями з переліків, а не за текстом.

### Вартість токенів — виміряно

Системний промпт із few-shot прикладами домінує: близько **1 900 вхідних
токенів на запит** проти ~150 вихідних. Тобто платимо переважно за те, щоб
щоразу заново пояснювати моделі ті самі правила.

Не закрито:
- **Немає кешування промпту.** Системна частина незмінна між запитами — це
  канонічний випадок для prompt caching, який дав би найбільшу економію.
- **Немає батчингу.** Кілька запитів в одному виклику різко скоротили б вхідні
  токени, але зв'язали б їхні долі: один невалідний JSON завалив би всю пачку.
  Свідомий обмін надійності на ціну; на цьому обсязі надійність важливіша.

### Квоти безкоштовного тіру — закрито, але боляче

Найдорожчий урок цієї задачі, і він коштував двох невдалих прогонів:

| Що я думав | Що виявилось насправді |
|---|---|
| ліміт 15 запитів/хв | `gemini-3.5-flash`: **5/хв і 20/добу** |
| `models.list` показує доступні моделі | показує й ті, що 404-ляться для нових ключів |
| `retryDelay: 59s` означає «почекай хвилину» | для добової квоти це неправда — вона не звільниться сьогодні |

Через третій рядок перший «виправлений» прогін молотив **25 хвилин і 54 марні
виклики**, щоб зрештою завалити всі 18 рядків. Тепер добова квота
розпізнається окремо (`quotaId` містить `PerDay`), піднімає `RunGuard` і
зупиняє прогін за секунди, а не за пів години.

Дефолтна модель обрана **за розміром добової квоти, а не за якістю**:
`gemini-3.5-flash` із її 20 запитами на добу фізично не може обробити інбокс із
18 рядків, якщо хоч один піде на ретрай. На платному ключі варто брати старшу
модель.

### Ін'єкція через текст запиту — закрито частково

`raw_text` пишуть люди, і REQ-014 уже містить URL. Текст обгорнутий явними
маркерами, у системному промпті сказано не виконувати вказівок ізсередини й не
ходити за посиланнями, і сервіс ніде не звертається до URL із даних.

Не закрито: немає перевірки *постфактум*, що модель таки не пішла за
інструкцією з тексту. Для інбоксу від колег ризик низький; для публічної форми
я б додав окрему перевірку виводу.

### Що система не вміє в принципі

- **Не бачить дублікатів.** REQ-013 — це той самий звіт, що й REQ-001, лише від
  іншої людини з тієї ж команди. Кожен запит класифікується ізольовано, тож
  зв'язок не виявляється. Це найпомітніша прогалина на цих даних.
- **Не знає контексту.** Ні історії треду, ні особи відправника, ні того, що
  вже в роботі.
- **Закритий словник відділів** може підштовхнути модель обрати найближчий
  наявний варіант замість чесного `null`. Компроміс свідомий: без нього звіт
  розсипається на різні написання того самого відділу.
- **Немає розміченого набору для оцінки.** Це найбільша чесна прогалина:
  без нього неможливо ані виміряти точність, ані помітити регресію після
  правки промпту. Усі судження про якість у цьому README — це очима, на 18
  рядках.

## Що зробив би далі

За спаданням цінності:

1. **Розмічений набір і метрика.** 30–50 рядків із проставленими вручну
   мітками, `accuracy` по кожному полю, прогін у CI. Без цього будь-яка зміна
   промпту — це здогадка, а не покращення. Усе інше в цьому списку менш важливе.
2. **Дедуплікація.** Другий прохід по вже структурованих запитах: ембедінги
   `short_summary` + поріг схожості. Зловив би REQ-013 ↔ REQ-001.
3. **Кеш і чекпоінти.** Хеш `raw_text` + версія промпту як ключ. Робить
   повторні прогони безкоштовними, а падіння — невтратним.
4. **Замикання циклу з замовником.** `clarifying_questions` уже готові до
   відправки — лишається дописати їх ботом у тред, звідки прийшов запит.
   Найкоротший шлях від «структурованих даних» до реально збереженого часу.
5. **Prompt caching** для системної частини.
6. **Калібрування `confidence`.** Зараз модель ставить 0.9 майже всюди —
   поріг у бізнес-правилі R3 підібраний, а не обґрунтований даними.

## Тести

```bash
./.venv/bin/pip install -r requirements-dev.txt
./.venv/bin/python -m pytest -q
```

Мережі не торкаються, ключа не потребують, час замокано — уся сюїта менш ніж
за секунду. Найцікавіше в ній не щасливий шлях, а шляхи відмови: биті JSON,
порушення схеми, 429, таймаути й мертвий ключ не повинні призводити до втрати
рядка чи до безглуздих ретраїв.

```

  models.py      словники + строга схема + нормалізація вивертів моделі

  pipeline.py    async-оркестрація, rate limiter, ретраї, гарантія 1-до-1
  report.py      output.json + report.md
  config.py      налаштування з оточення, вибір провайдера
  cli.py         точка входу
  llm/
    base.py      LLMClient ABC + типізовані помилки
    gemini.py    Gemini: structured output, temperature 0, seed, retry-hint
    fake.py      офлайн-стаб для тестів і демо
```
